Öffentliche API-Bereitschaft wird geprüft. Verwaltungsdaten erfordern eine Anmeldung.

Eine AMU-Anwendung sicher verbinden
  1. Als Administrator unter „Anwendungen“ einen eigenen Namen anlegen. Für Chat genügt die Rolle Inferenz mit Modell- und Chat-Freigabe.
  2. Den einmaligen Schlüssel geschützt in der Anwendung speichern. Über „Verbindungskonfiguration“ das zugehörige Profil aufrufen.
  3. Auf diesem Computer funktioniert die lokale Adresse. Auf einem zweiten Computer eine private HTTPS-IP oder Domain mit passendem Zertifikat und öffentlicher CA verwenden.
  4. Für LAN zuerst Zertifikat, Bind-Adresse und erlaubtes Subnetz prüfen. Firewall-Freigaben separat genehmigen lassen. Den Schlüssel niemals in eine URL schreiben.
  5. Vom Client zuerst Modelle auflisten, dann eine kurze Antwort und Streaming prüfen. Ein lokaler Test bestätigt keine Verbindung zweier Computer.

Gesicherte Backups herunterladen und auf einem getrennten Medium speichern. Passwort/Wiederherstellungsschlüssel getrennt aufbewahren. Ein manueller Programm-Rollback erfolgt nur bei gestopptem Dienst nach der Betriebsanleitung; aktuelle Datenbanken und Zugänge bleiben erhalten.

Nicht angemeldet. Vorhandenen Administrator-Schlüssel eingeben; kein Zurücksetzen erforderlich.

Erlaubte Funktionen

Freigaben ergänzen die Rolle. Ohne ausgewählte Funktion bleiben diese APIs gesperrt. Tagesbudgets gelten nach UTC; Reservierungen schützen auch bei Abbruch und Neustart. Modell-RAM wird gemeinsam genutzt.



Server- und Ressourcenprofil
Portable CPU-, Kontext-, RAM- und Warteschlangenlimits. Änderungen werden gespeichert und beim nächsten API-Neustart aktiv. Mehrere isolierte Modell-Worker sind möglich. Die Summe ihrer Threads und RAM-Schätzungen wird vor jedem Start geprüft.

Weiteren Server sicher verbinden
Auf dem zweiten Server zuerst den AMU-Worker mit TLS und Quell-IP-Freigabe starten. Hier werden Identität, Vertrauenskette und Zertifikat geprüft. Es wird kein öffentlicher Port geöffnet.
Modell, Threads und Kontext werden auf dem entfernten Server konfiguriert. Ein gestoppter Gateway-Zugang entlädt dessen Modell nicht. Beim Ersetzen bestehender Zugangsdaten bedeuten leere Schlüssel-/CA-Felder: bisherigen Wert verwenden. Identität und Modell bleiben gebunden.


Verschlüsselte Sicherung und Wiederherstellung
Vollständige Sicherungen enthalten Daten und Rechte. Während der Aufnahme werden neue Anfragen kurz gesperrt; laufende Arbeit muss vorher beendet werden. Neue Pakete sind immer verschlüsselt.
Leer = lokaler Wiederherstellungsschlüssel in scratch/secrets/backup-recovery-key.txt. Für einen Serverumzug das eigene Passwort verwenden oder den lokalen Schlüssel getrennt und sicher übertragen.
Die Wiederherstellung überschreibt keine laufende Installation. Eine spätere Übernahme erfolgt nach Prüfung im gestoppten Zustand.
Automatische Sicherungen planen
Sichert nur bei Leerlauf. Verpasste Termine werden einmal nachgeholt. Jede geplante Sicherung wird danach entschlüsselt und auf Integrität geprüft. Keine automatische Übernahme alter Datenbanken. Ausreichenden Speicherplatz und getrennt gesicherten Wiederherstellungsschlüssel vorhalten.
Aufbewahrung und geschützte Wiederherstellungspunkte
Nur verifizierte planmäßige Sicherungen können entfernt werden. Manuelle Sicherungen, angeheftete Archive und die letzten zwei geprüften Vollsicherungen mit Modellgewichten bleiben erhalten. Bestehende Sicherungen ohne Herkunftskennzeichnung werden nicht automatisch gelöscht.
